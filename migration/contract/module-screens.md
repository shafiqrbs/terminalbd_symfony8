Row counts, not markup: the two render different HTML by design, but they must be
looking at the same rows under the same tenancy. `twig rows` is what the Twig table
renders on its first page; `api page` is the API at that controller's page size.

aggregate queries shown together, and its Twig page draws a skeleton - 12 months, 31
days - whether or not the data fills it, so what is compared is that both sides answer
and run the same queries. A SETTINGS screen has one row per tenant and nothing to
count. The DASHBOARD produces a redirect, and is compared by where each side sends
the user.

**`color`** - Twig 500 in both trees: ColorController does findBy(['isValid' => 1]) and ProductColor has no such field. The port answers what the screen meant - name ASC - rather than reproducing the exception.

**`medicine_purchase_new`** - Twig 500: PurchaseController::newAction asks getAccountingConfig()->isAccountClose() and this tenant has no accounting config. Data, not a port defect - and the API answers with the cart.

**`medicine_report_purchase_vendor_details`** - Twig 500 in both trees, same cause as System Overview: getMainApp() is null for this tenant.

**`medicine_sales_customer_item`** - The Twig screen renders its items into a table it builds in JavaScript, so there is no tbody to count on load.

**`medicine_sales_temporary_new`** - Twig 500: SalesTemporaryItemType reads an undefined property config. A form type is presentation and does not exist in the API, which answers with the cart.

**`medicine_system_overview`** - Twig 500 in both trees: AccountPurchaseRepository asks getMainApp()->getSlug() and this tenant has no main application. The API fails identically, on the same line, in the copied code.

A screen with 0 rows on both sides is agreement, not evidence: this dump's tenant
has no rows for several of these tables. That is the same constraint every other
harness in this migration reports.
