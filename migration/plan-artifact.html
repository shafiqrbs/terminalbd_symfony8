Migration plan · drafted 3 September 2026

Terminalbd on Symfony 8

A ten-module multi-tenant SaaS — hospital, pharmacy, restaurant, inventory, accounting — running on a framework that reached end of life in November 2018. This is the route off it: a strangler migration onto a parallel Symfony 8.1 application sharing the same MySQL database, with modules moved one at a time behind the reverse proxy. Phase 1 is built and verified.

01 · Shipped and verified

The entity graph is ported

The whole Doctrine model moved in one pass, because it had to. Measured across the tree, 48% of targetEntity references cross a bundle boundary and every module depends on between two and fifteen others. There is no clean per-module seam in the data model, so a partial copy would leave Doctrine unable to resolve its own metadata. The model is the shared foundation; the HTTP layer is what moves module by module on top of it.

Reproduced by migration/bin/port.sh, which is idempotent — it rebuilds next/src/ from the untouched SF 2.8 tree in seven steps and re-runs safely after any change to the legacy code. Acceptance is next/bin/validate-mapping.php, which boots the kernel and loads every Doctrine metadata definition without touching a database. The 30 entities still reporting errors are pre-existing defects, covered in section 04.

04 · Findings

Latent bugs the port surfaced

Doctrine 2 and PHP 7 tolerated a lot silently. Moving to strict attribute parsing turned each of these into a hard error, which is how they were found. All of them are pre-existing — the same text is in the SF 2.8 tree today.

Highest severity · would have silently destroyed authorization

DBAL 4 removed the array and object column types outright. 24 live columns hold PHP-serialized payloads — including fos_user.roles, which carries every user's role set. Read through a naive json replacement, every user on every tenant silently loses their roles. Fixed with a compatibility type (App\Doctrine\Type\LegacyArrayType) that reproduces DBAL 3 semantics exactly, so production rows are read unchanged and no data migration is required.

1

Composite foreign key introduced by automated conversion

A stray * in a User docblock left @ORM\JoinColumns malformed. Rector faithfully emitted both join columns as separate attributes on User::$globalOption, which ORM 3 reads as a composite FK against a table that has one column. Merged back to the single column Doctrine 2 actually used. Found by scanning all 686 files for the pattern — it produces no error message of its own, just a wrong schema.

30

JoinColumn on illegal association sides

Placed on OneToMany relations, on inverse (mappedBy) sides, and in three cases on plain scalar columns. Inert under ORM 2, a hard mapping error under ORM 3. Removed by rule, preserving the legitimate owning-side ManyToMany pairs.

98

cascade={"merge"} after merge() was removed

ORM 3 deleted EntityManager::merge() and its cascade. The app calls merge() exactly once, in a development command, so the cascade was already inert — dropped and the option lists deduped.

5

Duplicated non-repeatable annotations

Four classes declare @ORM\Entity twice, and one property declares @ORM\OrderBy twice with conflicting sort directions. Doctrine 2 re-keyed annotations by class name so the last won; PHP 8 rejects the repeat outright. Collapsed keeping the last occurrence, which reproduces the ORM 2 outcome.

3

parent::__construct() in parentless classes

The method is named _constructor() — a typo for __construct() — so it was never called and the invalid parent call never executed. PHP 8 rejects it at compile time. Removing the unreachable line preserves behaviour byte-for-byte. The typo itself is left in place: fixing it would activate three constructors that have never run.

48

Broken bidirectional associations

Across 30 entities, inversedBy / mappedBy point at fields that do not exist on the other side. Doctrine only resolves the inverse side lazily, so these never surfaced at runtime. Catalogued in migration/contract/broken-associations.md — fix each as its module is ported, by adding the missing field or making the relation unidirectional.

2

Namespace and registration inconsistencies

appstore\Bundle\DomainUserBundle is declared with a lowercase leading character, which only works because nothing resolves it case-sensitively; and Appstore\Bundle\DmsBundle exists on disk but is never registered in AppKernel. Both normalised during the namespace rewrite.

05 · Roadmap

Phases, in dependency order

These are genuinely sequential — each phase unblocks the next. Phases 3 onward ship module by module, each independently deployable, with rollback being a single route flipped back at the proxy.

01

Skeleton and entity graph

shipped

Symfony 8.1.6 on PHP 8.5 in next/, sharing the production MySQL database. All 335 entities and 327 repositories lifted into App\, annotations converted to attributes, mappings validated. FOSUser and FOSComment superclasses reproduced column-for-column from their locked revisions so they map onto fos_user, user_group and the comment tables untouched.

02

Authentication and tenancy

The gate for everything else — no module can move until a request can be authenticated in the new app.

  • Native Symfony security replacing FOSUserBundle's 12 route names and its user manager
  • Migrating password hasher: verify existing salted sha512, transparently rehash to a modern algorithm on next successful login — no forced reset for any tenant
  • Port the subdomain tenancy listener that resolves each tenant from its host
  • Shared session store so a user stays logged in across the proxy boundary while both apps serve traffic
  • Convert the 112 files of @Secure annotations and the ~200-entry role hierarchy
03

Mobile APIs

wire-locked

96 endpoints across /flutter-api (66), /android-api (24) and /android-api-portal (6), with shipped clients that cannot be updated in lockstep. The contract is already extracted to migration/contract/api-endpoints.json; the capture and shape-diff harness is written and waiting on credentials.

  • Record golden responses from production: php migration/bin/capture.php legacy
  • Port controllers off FOSRestBundle onto native controllers plus the Serializer
  • Gate every deploy on compare.php, which diffs response shape and status — keys and value types, not volatile ids or timestamps
04

Shared presentation layer

Built once, consumed by every module port that follows: base layouts on Twig 3, the Bundle:Dir:file.twig → @Dir/file.html.twig rename across 1,854 references, Assetic replaced by AssetMapper, and the PDF and ESC/POS thermal-receipt pipelines re-plumbed off the abandoned wkhtmltopdf shims.

05

Module ports

Ten modules in the order set out in section 06, smallest first to prove the pipeline before the large modules commit to it. Each port converts its controllers to autowired services, its form types to the SF8 API, and its templates to Twig 3 — and fixes that module's share of the 48 broken associations.

06

Decommission

Retire the PHP 7.4 pool once the last route is served by the new app, collapse the proxy rules, and drop the compatibility shims that are no longer reachable. The LegacyArrayType stays until its 24 columns are migrated deliberately, with a backfill — not as a side effect of a port.

07 · Open risks

What could still go wrong

RiskWhy it mattersMitigation
No test suite Nothing catches a regression in 700k lines of untested code The golden-response harness covers the 96 mobile endpoints. Extend the same record-and-diff approach to the highest-traffic HTML routes before porting each module — it is cheaper than retrofitting unit tests
Symfony 8.1 reaches EOL Jan 2027 The migration will outlive the target release Minor Symfony upgrades are backward compatible. Plan to ride 8.2 → 8.3 → 8.4, which is the next LTS (Nov 2027). Budget a day per bump, not a project
Shared database, two writers Both apps write the same tables during the transition Schema changes are additive-only until decommission. Never let a port alter a column the legacy app still reads
Serialized array columns 24 columns readable only through the compatibility type Keep LegacyArrayType registered for the full migration. Convert to json later as a deliberate backfill with its own rollback
Mobile clients cannot be updated in lockstep A shape change breaks apps already in users' hands compare.php gates every API deploy; treat a drift report as a release blocker, not a warning
Password rehashing is one-way Users who never log in during the transition keep sha512 hashes Expected and safe — the migrating hasher verifies both formats indefinitely. Do not remove the legacy hasher on a schedule; remove it when telemetry shows zero legacy hashes remain

Not yet possible in this environment: the legacy app has no vendor/, no app/config/parameters.yml and no reachable database, so nothing has been run against real data. Golden-response capture and any schema comparison need a pointer at a staging environment.
